# Phase 5 · 待办收件箱统一（决策中枢）

> 目标：后端 ReviewItem 升级为原型的五类卡片模型；effect 后端事务执行；
> 实时派生项语义后端化；badge 按作品隔离。
> 依赖：Phase 3（effect 要写目录）。

## 后端现状（已核实）

- `routes/review.py`：`GET/POST /api/v1/review-items`、`GET /{id}`、`approve/release/reject`、`human-review-events` + `actions`。
- `routes/projects.py`：`backtrack-items` + `POST …/{item_id}/resolve` —— **这是「resolve 时后端执行动作」的现成先例**，扩展 ReviewItem 前先读它的实现模式。
- **开工核对**：ReviewItem 现有列与状态机（approve/release/reject 的语义），决定是「扩展原表」还是「新增卡片层引用原表」；倾向**扩展原表**（一个收件箱不许有两套真相）。结论记 PROGRESS.md。

## 改动 1 · 卡片数据模型（对照 `design/ws-review.jsx` 与契约附录）

ReviewItem 增列（JSON 为主）：
- `kind`(decision|risk|qc|idea|note)、`priority`(1|2|3)
- `provenance_json`：`{source, where, occurred_at}`（source 取值见原型 RV_KINDS 各卡：风格参考/文学质检/构思/章节编排/时间线/控制塔…）
- `card_json`：`{detail, preview:{before,after}?, checklist?:[], options?:[]}`
- `actions_json`：`[{label, intent(primary|ghost|quiet), op(resolve|nav|snooze), nav_to?, nav_step?, effect?:{type, …payload}}]`
- `state`(open|resolved|snoozed) + `snooze_until` + `resolved_action_index`
- `dedupe_key`(str, 与 project_id 联合唯一索引，可空)——Phase 7 的 `onceTask` 靠它
- 既有 approve/release/reject 流保留给旧生产者，新卡片走 `resolve`；两套状态在响应里映射为统一 `state`。

## 改动 2 · effect 后端事务执行（⚖️ D4）

`POST /api/v1/review-items/{id}/resolve` body=`{action_index}`：同一事务里执行 effect 并置 resolved。首批 effect 类型：

| type | 行为 | 复用 |
|---|---|---|
| `insert_scene` | `{chapter_id, at, scene:{title,kind,brief}}` 插场景 | `services/catalog.py` 服务函数（Phase 3） |
| `rename_chapter` | `{chapter_id, title}` | 同上 |
| `bind_style_profile` | `{profile_id}` 画像绑定到项目 | `style_reference` 既有绑定服务 |
| `rule_canon` | `{finding_id, value}` 设定裁决 | `longform/audit adjudicate` 服务（Phase 7 接通） |
| `create_entity` / `add_timeline_event` | 资料库入库 | Phase 6 服务 |

effect 注册表放 `services/review_effects.py`：`{type: handler}`，handler 签名 `(session, project_id, payload) -> result`；未知 type 返回结构化错误。`POST …/{id}/unresolve` 撤销标记（不回滚 effect——卡片上注明，复杂逆操作不做）。

## 改动 3 · 实时派生项（原型 `rvDerived()` 的后端化）⚠️ 语义核心

- 新增 `services/review_derived.py`：纯读函数，从真相算出派生卡（首批三类，照抄 `design/ws-review.jsx` `rvDerived`：雪花步骤空缺/不完整、起草队列异常、目录结构异常如空章）。
- `GET /api/v1/review-items?state=open` 响应 = 持久卡 ∪ 派生卡。派生卡 `live:true`、id=内容指纹（如 `derived:snowflake:{step}:{hash(残缺字段)}`）。
- **三条语义必须保留**：① 不可无动作 resolve（端点拒绝）；② 源头修好下次 GET 自动消失；③ 指纹变化即重新浮现（即使曾 snooze——snooze 记录按指纹 id 存）。
- 派生项 snooze：持久表存 `{fingerprint, snooze_until}`。

## 改动 4 · 生产者改造 + badge

- 既有生产者（QC 阻塞、安全标记、triage 异常）逐个补 kind/priority/provenance/actions；风格学习完成（style_reference materialization）产 decision 卡（preview 用画像的 before/after 例句）；控制塔冲突卡留给 Phase 7。
- `GET /api/v1/review-items/badge?project_id=…` → `{count}`（=priority 1 的 open 数，对齐 `rvBadge`）。

## 改动 5 · 前端接入

- 待办 store 全函数换 API（契约附录）；`rvDerived` 前端实现删除（由后端供给）。
- 「今日已处理 N 件」计数：resolve 响应带 `done_today`，或前端本地数（UI 偏好级，允许 localStorage）。
- 一次性迁移：旧 `ws_review_v1::<workId>` 的 custom 项上行；resolved/snoozed 状态尽力迁移，迁不动的丢弃（卡片可再生）。

## 自检

- 风格画像学完 → decision 卡出现 → 「应用到本项目」→ 绑定生效、卡消失、badge 减一。
- QC 卡「采纳·插入反应场」→ 目录真的多一个反应场（编排台可见）。
- 删掉雪花某步内容 → 派生卡浮现 → 不可划掉 → 补全后自动消失。
- 同一 dedupe_key 投两次只有一张卡。
- `pytest -k "review_item or review_effect or review_derived"` 绿；全量绿。提交：`FE-ALIGN Phase 5: unified review inbox`。
