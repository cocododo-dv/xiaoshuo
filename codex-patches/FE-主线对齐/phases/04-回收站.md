# Phase 4 · 回收站（场景/章节/作品三级软删 + 整体恢复）

> 目标：原型回收站视图（trash）接真；删除任何层级都可整体恢复。
> 依赖：Phase 3（目录统一后才有可软删的真行）。

## 后端现状（已核实）——**章级与场景级都已存在，不是从零设计**

- 章级（`routes/chapters.py`）：`POST /api/v1/chapters/trash|restore|purge`、`GET /api/v1/author-trash`。
- 场景级（`routes/scenes.py`）：`POST /api/v1/scenes/trash|restore|purge`。
**开工第一步**：读两套的 `services/` 实现（软删标记还是移表？是否同一服务？恢复语义？），结论记入 PROGRESS.md，然后**扩展同一机制**。本 Phase 的实际缺口：**作品级软删 + 三级统一回收站列表 + 前端接入**。

## 改动 1 · 三级软删

- 统一模式：`deleted_at`(nullable) + `deleted_by` 加到 `StoryProject` / `ChapterGoal` / `SceneCard`（若既有章级机制已是软删标记，沿用其列名约定）。
- 所有列表/聚合查询默认过滤 `deleted_at IS NULL`（catalog、dashboard、flow-status、review 派生都要检查）。
- 级联：删作品 = 标记本体 + 旗下章/场景/待办/构思**不动数据只动可见性**；恢复 = 清标记，全链路回来。
- 场景软删时正文文档保留（恢复即回——对齐原型「正文文档一并保留」语义）。

## 改动 2 · 端点

| 端点 | 语义 |
|---|---|
| `DELETE /api/v2/projects/{id}` | 整部软删 |
| `POST /api/v2/projects/{id}/restore` | 整部恢复 |
| `DELETE …/catalog/chapters/{id}` / `POST …/restore` | 章级（桥接/复用既有 v1 chapters trash 服务） |
| `DELETE …/catalog/scenes/{id}` / `POST …/restore` | 场景级（桥接/复用既有 v1 scenes trash 服务） |
| `GET /api/v2/trash?project_id=…` | 合并列表：`[{id, kind(work|chapter|scene), title, removed_at, restorable}]`；`project_id` 省略时含已删作品（对齐原型「全局桶 + 作品桶」） |
| `DELETE /api/v2/trash/{entry_id}` | 永久清除（⚖️ D3 默认：仅手动；自动清理不做） |

## 改动 3 · 前端接入

- `WsTrashStore.list/restore/purge/clear` 换 API；`push` 退化为兼容壳（软删端点自动产生条目）。
- `WsWorks.remove` 恢复显示，改调 `DELETE /projects/{id}`；删除「种子不可删」与「最后一部不可删」前端限制中的前者（demo 项目由后端 `is_demo` 决定是否可删，⚖️ 默认：demo 可删可恢复）。
- 写作器删场景改走场景软删端点。

## 自检

- 删整部书 → 切换器消失 → 回收站可见 → 恢复 → 章节/构思/待办/统计全部回来。
- 删场景 → 恢复 → 正文原样回来（包括未保存前的最后版本）。
- 永久清除后 `GET catalog` 与统计无残影。
- 级联测试：`pytest -k "trash or soft_delete"` 绿；全量绿。提交：`FE-ALIGN Phase 4: trash`。
