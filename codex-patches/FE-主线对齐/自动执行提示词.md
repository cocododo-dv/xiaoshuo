> 用法：把 `FE-主线对齐/` 放进仓库 `codex-patches/` 后，在仓库根目录启动 Claude Code，
> 粘贴下方提示词。建议用 `claude --dangerously-skip-permissions`（或预先在 settings 里
> 放行 Bash/Edit/Write），否则每次命令都会停下来等确认，做不到无人值守。

---

你要在本仓库执行一项长期改造任务：以高保真原型为正式前端，对齐后端。**全程自动执行，不要停下来向我提问。**

## 任务材料（按此顺序通读后再动手）

1. `codex-patches/FE-主线对齐/CLAUDE_CODE_任务简报.md` — 主简报
2. `codex-patches/FE-主线对齐/契约附录-store缝合面.md` — 前端 store 不可变接口
3. `codex-patches/FE-主线对齐/契约附录-B-后端端点清单.md` — 已核实的后端端点
4. `codex-patches/FE-主线对齐/phases/00-基线与陷阱.md` — 含对主简报的三处事实修正
5. `codex-patches/FE-主线对齐/PROGRESS.md` — 进度账本（**每次开始先读它，从未完成的 Phase 续起**）

## 执行规则

1. 决策点 D1–D6 **全部按默认方案**，不要询问。
2. 按 Phase 0→8 顺序执行，phases/ 目录每个 Phase 一份简报。每个 Phase 完成的定义：
   - 该 Phase 简报的「自检」全部通过；
   - `cd backend && python -m pytest` 全绿（前端 Phase 另加 `npm run build` 通过）；
   - 用简报规定的提交信息 `git commit`；
   - 更新 PROGRESS.md（勾选 + 提交号 + 核对发现）。
   全部满足后**直接进入下一个 Phase，不要等我确认**。
3. 遇到简报与实际代码不符：以代码为准，把差异记入 PROGRESS.md「核对发现」，继续执行。
4. 遇到需要权衡的小决策：选与「总体原则」和既有代码风格最一致的方案，在 PROGRESS.md 记一行理由，继续执行。**禁止以提问的方式停下来。**
5. 卡死处理：同一问题尝试 3 种修法仍失败 → 在 PROGRESS.md「遗留/例外」记录（问题、已试方案、影响面），把该小项标记为 DEFERRED，继续该 Phase 余下工作；若整个 Phase 被阻塞，记录后跳到下一个不依赖它的 Phase。**任何情况下不允许：回退掉已完成 Phase 的提交、用伪造/跳过测试的方式让测试变绿、删除用户数据迁移逻辑。**
6. 上下文管理：每完成一个 Phase 执行 /compact（或等效收缩）；如会话中断，重启后第一件事是读 PROGRESS.md 和 `git log --oneline -20` 恢复现场。

## 红线（违反任何一条都算失败）

- 前端改造**只动 store 层，不动视图层**；契约附录 store缝合面 列出的方法签名、数据形状、事件一个都不许变。
- 不修改 `codex-patches/FE-主线对齐/design/` 下的任何文件（它是设计真相源，只读）。
- 不修改既有 Vue `frontend/` 的业务代码（D6 之前它保持可用）。
- 不做简报范围之外的「顺手重构」；发现的题外问题记 PROGRESS.md，不修。
- 数据库改动一律走 alembic 迁移；保持 `alembic heads` 单头。
- 每个 Phase 一次提交，禁止把多个 Phase squash 在一起。

## 完成标准

Phase 0–8 在 PROGRESS.md 中全部勾选，主简报「全局验收」5 条逐条验证通过，最后输出一份简短总结（每个 Phase 的提交号 + 全部 DEFERRED 项清单）。

现在开始：读完五份材料后，从 PROGRESS.md 中第一个未完成的 Phase 开始执行。
