# 结果闭环治理二次收敛设计

> 日期：2026-07-13
>
> 基线：`main@ab1550f`
>
> 输入评估：`docs/superpowers/specs/2026-07-13-ai-novel-outcome-governance-completion-assessment.md`
>
> 执行分支：`codex/outcome-governance-closure`
>
> 决策：按阻断优先级串行推进；常规技术选择由执行者自主决定，仅在真人盲评必须由用户操作时暂停。

---

## 1. 目标与边界

本设计的目标不是继续增加文学模块，而是把现有治理基础设施推进到可复算的结果闭环：

1. 运行数据库、迁移和证据状态一致。
2. 参考文本没有未授权云发送和提示词注入旁路。
3. 所有 LLM 调用可记账，场景预算能在调用前阻止超支。
4. 五章北极星从 UI 完整执行并通过结果门。
5. 真实 30 组人类盲评驱动 Best-of-N 默认策略。
6. 真实 30 章耐久运行通过恢复、延迟、成本和质量硬门。
7. 指标与结构收敛在结果门稳定后完成。

非目标：

- 不新增文学评分维度、外围页面或无关模型能力。
- 不在安全和结果门未通过前做大规模样式重写。
- 不把合成数据当作真实模型、真人或生产结论。
- 不直接修改未经备份验证的现有数据库。

## 2. 总体架构

闭环拆成六个严格串行、可独立验收的子项目：

```text
C0 运行真值与证据
  ↓
C1 来源安全与成本硬约束
  ↓
C2 UI 五章北极星
  ↓
C3 真人盲评与默认策略
  ↓
C4 30 章耐久与 FK 决策
  ↓
C5 指标与结构收敛
```

每个子项目都必须完成：失败测试、最小实现、定向验证、相关回归、证据 manifest、进度状态更新。前一阶段未通过时，后一阶段可以准备测试夹具，但不得宣布进入完成态。

## 3. C0：运行真值与证据

### 3.1 数据库策略

- 现有 `backend/novel_system.db` 只读盘点，不原地试迁移。
- 使用在线备份工具生成校验通过的快照，再复制为迁移演练库。
- 演练库从当前 revision 升至 head，依次验证 metadata drift、孤儿、关键表列和 API smoke。
- 只有演练通过后才允许对实际运行库执行同样步骤。

### 3.2 Evidence manifest

新增统一 schema，至少包含：

```json
{
  "schema": "outcome-evidence-v1",
  "run_id": "string",
  "git_commit": "string",
  "database_revision": "string",
  "config_hashes": {},
  "model_routes": {},
  "provenance": "synthetic|offline|real_model|human",
  "commands": [{"command": "string", "exit_code": 0}],
  "artifacts": [{"path": "string", "sha256": "string"}],
  "gates": [{"code": "string", "passed": true, "details": {}}]
}
```

`synthetic` 和 `offline` 只能证明工具或确定性行为，不得满足真实模型、真人或发布门。

### 3.3 状态语义

进度记录拆为三列：`engineering_status`、`real_gate_status`、`release_gate_status`。历史“已完成”若只有 L1/L2 证据，必须降为“工程实现完成、真实门待验”。

## 4. C1：来源安全与成本硬约束

### 4.1 权属门

- `cloud_policy != local_only` 必须同时满足 `declared=true` 与 `send_rights=true`。
- 未声明时只允许 local-only；接口返回稳定错误码，不静默改变云发送权限。
- 存量非本地策略且未声明的记录进入盘点，运行时强制按 local-only 处理，直至用户重新声明。

### 4.2 不可信数据边界

在 style-reference 公共 LLM 出口声明 typed untrusted fields，而不是由每个调用点自行拼接。原文、段落、quote、evidence、few-shot 和 RAG 均先中和疑似指令，再放入显式数据边界；系统任务、schema 和角色指令始终位于边界外。

### 4.3 统一调用账本

- `run` 与 `run_task` 共用 LLM call persistence。
- provider 没有 usage 时使用本地估算，并标记 `usage_is_estimate=true`。
- 失败调用记录已经消费或预留的 token，不得按 0 消失。
- 调用发起前原子预留，完成后按实际用量冲正；取消释放未消费预留。
- 场景生命周期预算、次数预算任一耗尽即停止自动新调用；topup 仍是唯一扩容入口。

### 4.4 取消语义

新增显式取消动作，只取消尚未开始的新节点；已完成调用、草稿和账单不回滚。取消、预算耗尽和普通失败使用不同状态与审计事件。

## 5. C2：UI 五章北极星

### 5.1 六阶段 UI 约束

`snowflake_planning`、`materialization`、`scene_execution`、`candidate_selection`、`archive`、`chapter_aggregation` 必须全部由浏览器交互触发并记录 `lane=ui`。API 只读取并断言最终服务端真值。

### 5.2 两条真实 lane

- 原创 lane：不使用参考书，验证纯主链。
- 来源安全 lane：只使用授权或公版文本，验证权属、注入和来源报告。

两条 lane 均固定输入、配置哈希和模型路由。任何空稿、未归档、恢复失败、Q0/Q1 未解决或来源泄漏都使整轮失败。

### 5.3 恢复检查

在归档后清除 localStorage、重启后端并重新加载页面；正文、候选选择、场景状态和章节聚合的哈希必须保持一致。

## 6. C3：真人盲评与默认策略

- 准备 30 个不同冻结快照，生产终选内容与实验内容隔离。
- 前端投票前只返回左右纯文本；投票后才 reveal。
- 平局记录但不计非平局样本，持续采集到 30 个非平局。
- 用户本人只负责阅读并选择；系统负责准备、匿名化、持久化、统计和报告。
- `upgrade_to_default` 才允许关键场默认 Best-of-N；其余结果默认单发并保留显式可选入口。
- 应用默认策略是单独的幂等、可审计动作，不能由报告生成隐式修改。

## 7. C4：30 章耐久与 FK 决策

- 使用真实持久化运行 30 章，在第 5/10/20/30 章执行清缓存和重启恢复。
- 每五章采集连续性、声音漂移、跨章重复、伏笔债、数据库大小、查询 p95、token 和成本。
- 漂移与重复按模型分层，不混算不同模型基线。
- 真实全量孤儿为 0、迁移和回归均通过后，再启用 SQLite FK；启用失败则回滚配置，不回滚已经验证的备份。

## 8. C5：指标与结构收敛

### 8.1 指标

后端统一聚合原设计 §10 的 15 个指标和北极星指标。所有分母为 0 的情况返回 `null` 与样本数，不伪造 0% 或 100%。UI 只展示后端结果，不自行重算。

### 8.2 结构

- 按已修改责任边界拆分 orchestrator、qc_engine、ws-snow 和 models。
- 页面使用 React lazy import；共享 client 不重复打包。
- 保持主 JS gzip <500KB，并以关键 UI E2E 防止拆分后的加载回归。

结构改造必须排在真实结果门之后，避免同时改变行为和文件边界。

## 9. 错误处理不变量

1. 已持久化的有效正文不因 QC、索引、成本、实验或指标失败而删除。
2. 数据库迁移前必须存在可校验、可恢复的备份。
3. 未授权文本不得发送云端，失败时保留本地数据但停止云调用。
4. 预算预留失败不得发起 LLM 请求。
5. 合成产物必须显式标记，不能满足真人或真实模型门。
6. harness 失败必须保存已完成阶段和具体失败证据。
7. 默认策略只能由具备正确 provenance 的报告驱动。
8. 任何自动流程不得重置场景生命周期预算或作者选择。

## 10. 测试策略

每项行为严格执行红—绿—重构：

- 单元：权属矩阵、不可信字段序列化、预算预留/冲正、manifest schema、指标分母。
- 集成：迁移副本、所有 LLM 出口记账、取消不回滚、策略应用幂等、FK 打开后的写路径。
- React：候选终选、实验投票、恢复水合、lazy 页面加载。
- 浏览器：六阶段 UI、原创五章、参考文本五章、清缓存和重启恢复。
- 真实模型：固定输入、固定路由、15 场结果门。
- 真人：30 个非平局盲评和报告复算。
- 耐久：30 章、四次恢复检查、p95、成本斜率和质量硬门。

普通 PR CI 运行确定性和离线测试；真实模型、真人和 30 章门进入受控发布 lane，但其结果必须由同一 manifest schema 记录。

## 11. 完成定义

只有以下条件同时满足，二次收敛才可标记完成：

- C0–C5 的工程门全部通过。
- 原创与参考文本五章真实 lane 均通过。
- 30 个非平局真人盲评完成并已应用正确默认策略。
- 30 章真实耐久门通过。
- 所有发布证据具备 commit、配置、provenance、hash 和退出码。
- 进度账本不再把 L1/L2 基础设施误写为 L3/L4 结果完成。
