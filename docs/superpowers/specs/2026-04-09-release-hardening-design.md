# Release Hardening Design

> 日期：2026-04-09
> 目标阶段：在当前 Novel System P2 基线之上，补齐稳定性、测试与发布交付面，使当前分支达到“可验证、可审阅、可提交 Draft PR”的状态。

---

## 1. 背景与当前状态

当前仓库已经具备可运行的后端、前端与 demo seed 基线：

- 后端提供 FastAPI + SQLite 工作流、review/release/verify 路径与 Chroma 相关能力。
- 前端已迁移到 Vue 3 + Pinia，并具备最小 smoke test 与构建入口。
- `README.md` 已定义 Windows 常规验证链和 WSL Ubuntu 24.04 严格 Chroma 验证链。

当前缺口不在业务功能，而在交付完整性：

1. 验证入口仍分散在 README 和多个目录脚本里，缺少统一的“本地一键验收”方式。
2. 仓库根目录缺少明确的 CI 配置，PR 上无法自动重复执行基础回归。
3. 发版前需要同时跑 Windows 与 WSL 两条链路，但这一要求还没有被固化成清晰的检查清单与交付说明。
4. 当前分支虽具备可运行基线，但还没有被整理成适合评审的提交面与 PR 面。

本阶段只解决这些交付问题，不扩展新的业务功能。

---

## 2. 目标

本阶段目标如下：

1. 提供稳定、明确、可重复执行的验证入口，覆盖：
   - Windows 常规后端测试
   - 前端测试与构建
   - WSL 严格 Chroma 验证
2. 在 GitHub 上建立最小够用的自动化 CI，确保 PR 至少能自动校验：
   - 后端非 `chroma_integration` 测试
   - 前端测试
   - 前端构建
3. 补齐文档与检查单，使“日常开发验证”和“发布前验证”边界清晰。
4. 将当前工作整理、提交、推送，并创建可直接审阅的 Draft PR。

成功标准：

- 开发者能从仓库文档快速找到统一验证入口，而不是手工拼装命令。
- GitHub PR 上存在可运行的基础回归工作流。
- WSL 严格 Chroma 链被明确定义为发布前必须通过的门槛，并能通过固定脚本触发。
- 最终 Draft PR 说明中包含已执行的验证结果与剩余风险说明。

---

## 3. 非目标

本阶段不处理以下事项：

- 不新增后端或前端业务功能。
- 不改写现有 API 合同。
- 不把 WSL 严格 Chroma 链强行塞进不稳定的 GitHub Actions 环境。
- 不引入版本号自动发布、自动 changelog、自动打 tag 等更重的发布流水线。

---

## 4. 方案对比与决策

### 4.1 方案 A：只补文档与手工命令

优点：

- 改动最少，最快完成。

缺点：

- 可重复性差，容易再次依赖人工记忆。
- PR 面缺少自动信号，评审成本高。

### 4.2 方案 B：平衡收尾方案

内容：

- 统一本地验证入口
- 建立 GitHub Actions 基础 CI
- 补齐文档、PR 模板或检查清单
- 完成提交、推送与 Draft PR

优点：

- 能把“稳定性”“测试”“交付”一起固化下来。
- 投入适中，符合当前收尾阶段目标。

缺点：

- 仍保留部分发布前检查为人工触发，而非全自动。

### 4.3 方案 C：重型发布工程化

优点：

- 自动化程度最高。

缺点：

- 明显超出当前“当前版本收尾”的边界。
- 会把注意力从交付当前版本转移到长期平台建设。

### 4.4 决策

采用 **方案 B：平衡收尾方案**。

原因：

- 它能在不扩张范围的前提下，把现有基线整理成真正可交付的状态。
- 它允许 GitHub 自动验证可稳定执行的部分，同时把 WSL 严格链保留为明确、可复现的发布前人工门槛。

---

## 5. 结构设计

### 5.1 验证入口层

新增统一验证脚本或命令入口，按职责分成三类：

1. Windows 常规链
   - 负责运行后端 `not chroma_integration` 测试
   - 负责运行前端测试与构建
2. WSL 严格链
   - 负责在 Ubuntu 24.04 下运行 `python -m novel_system.tools.chroma_smoke`
   - 负责运行聚焦 Chroma/verify/release 套件
   - 负责运行后端全量 pytest
3. 汇总入口
   - 提供发布前总入口或清晰组合方式
   - 让维护者能明确区分“PR 自动校验”与“发布前人工严格校验”

这些入口应优先放在仓库根或清晰的 `scripts/` 位置，命名应直接反映用途。

### 5.2 CI 层

新增 GitHub Actions 工作流，目标是提供稳定、低噪声的 PR 反馈：

- 使用 Ubuntu runner 执行后端非严格 Chroma 测试
- 使用 Node 环境执行前端测试与构建
- 在 PR 和主分支相关推送上触发

CI 不承担 WSL 严格 Chroma 验证，因为当前仓库明确依赖本机 WSL Ubuntu 24.04 作为真实写路径验证环境；这一点必须在文档中讲清，而不是伪装成“全部自动化”。

### 5.3 文档与交付面

文档需要形成三层信息：

1. `README.md`
   - 面向新进入仓库的人，给出最短的验证/启动路径
2. 收尾或发布说明文档
   - 面向当前版本交付，说明哪些检查需要在什么环境下运行
3. PR 模板或 PR 描述结构
   - 面向评审者，统一展示验证结果、风险和人工检查项

### 5.4 Git 交付面

本阶段完成后，应输出：

- 清晰的代码与文档提交
- 已推送的远端分支
- 一个 Draft PR

PR 内容必须包含：

- 变更概览
- 自动化验证结果
- WSL 严格链执行结果
- 剩余风险或后续建议

---

## 6. 数据流与执行流

### 6.1 开发者本地执行流

1. 在 Windows 环境运行常规验证入口。
2. 在 WSL Ubuntu 24.04 环境运行严格 Chroma 验证入口。
3. 收集结果并写入 PR 描述或交付说明。

### 6.2 GitHub PR 执行流

1. 开发者推送当前分支。
2. GitHub Actions 自动执行基础 CI。
3. 评审者在 PR 中同时查看：
   - 自动化检查状态
   - 人工填写的 WSL 严格验证结果

### 6.3 发布前检查流

1. 确认基础 CI 已绿。
2. 确认 WSL 严格 Chroma 链已绿。
3. 确认 Draft PR 描述中的检查单已填写完整。
4. 若无阻塞项，再转为 Ready 或继续发布动作。

---

## 7. 错误处理与约束

### 7.1 CI 与本地结果不一致

若 GitHub Actions 绿而 WSL 严格链失败，以 WSL 严格链结果为准，不得将当前版本视为可发布。

### 7.2 WSL 严格链无法全自动化

若严格链依赖当前机器上的 WSL 路径与本地环境，则必须显式记录前置条件、执行命令和成功标准，不得省略。

### 7.3 文档与脚本不一致

脚本命令是事实来源，文档必须引用或镜像脚本入口，避免 README 和脚本分叉。

### 7.4 PR 面信息缺失

若 PR 缺少验证结果、风险说明或严格链状态，即使代码无功能问题，也不视为完成交付收尾。

---

## 8. 测试设计

### 8.1 脚本与命令验证

- 验证新增本地脚本能正确调用现有测试/构建命令。
- 验证脚本失败时返回非零退出码，方便 CI 或人工检查。

### 8.2 GitHub Actions 验证

- 使用仓库已有命令而非重复定义逻辑。
- 确保工作流在干净环境中可安装依赖并完成执行。

### 8.3 文档回归

- 文档中的命令与脚本、CI 配置保持一致。
- PR 模板或说明结构与当前实际验证链一致。

---

## 9. 实施顺序

1. 盘点现有测试、脚本、文档和 GitHub 配置缺口。
2. 补齐统一验证入口。
3. 建立 GitHub Actions 基础 CI。
4. 更新 README 与发布/交付文档。
5. 增加 PR 模板或统一 PR 描述结构。
6. 运行 Windows 常规链与 WSL 严格链。
7. 整理变更、提交、推送并创建 Draft PR。

---

## 10. 验收结果定义

满足以下条件时，本阶段视为完成：

- 当前仓库能通过统一入口完成 Windows 常规验证。
- 当前仓库能通过固定入口完成 WSL 严格 Chroma 验证。
- GitHub PR 上存在可复现的基础 CI。
- 文档明确说明验证分层与发布门槛。
- 当前分支已推送，并已创建带验证信息的 Draft PR。
